Agentic Operations Platform on Google Cloud

An enterprise reference architecture for running IT, cloud and business operations through governed AI agents, built on Vertex AI and the wider Google Cloud estate, with in-house LLMs and SLMs serving the workloads that must stay inside our boundary.

Owner Office of the CTO, Enterprise Architecture Status Target-state blueprint v1.0 Scope ITOps, SRE, SecOps, FinOps, service management, business ops Companion AWS edition

1Intent and principles

Agentic Ops replaces ticket-driven, human-routed operations with a mesh of specialised agents that observe signals, reason over enterprise context, plan, act through governed tools, and learn from outcomes. Humans move from doing the work to setting policy, approving high-risk actions and handling novel situations.

The platform has to satisfy three constituencies at once: operators who need faster resolution with fewer pages, risk and compliance who need provable control over every autonomous action, and finance who need the cost of intelligence to fall per unit of work.

Agents are workloads, not features

Every agent has an identity, a versioned spec, an SLO, a budget, an owner and a kill switch. It is deployed, observed and retired like any production service.

Right model for the job

SLMs handle high-volume, narrow tasks; in-house LLMs handle restricted data; Gemini handles deep reasoning and multimodal. A central gateway decides, not individual teams.

Autonomy is earned

Each action type starts in shadow mode and graduates through autonomy levels based on measured precision, blast radius and reversibility.

Everything is a trace

Every perception, thought, model call, retrieval, tool call and approval is an OpenTelemetry span joined by one trace ID from trigger to outcome.

Policy outside the prompt

Guardrails are enforced by deterministic policy services at the gateway and tool boundary, never only by instructions in a system prompt.

Open protocols

MCP for tool access, A2A for agent-to-agent delegation, OpenTelemetry for telemetry, OCI images and Terraform for delivery. This limits lock-in at every seam.

3End-to-end flow

A signal enters at L0, passes the safety edge, is triaged by a cheap SLM, and is handed to the supervisor. The supervisor plans, delegates to domain agents over A2A, and each agent grounds itself in memory and knowledge before proposing actions. Every action passes the policy decision point, and, depending on autonomy level, a human gate, before touching production through an MCP tool. Outcomes feed back into memory, evaluation and training.

Autonomy levels

Autonomy is set per action type, not per agent. The incident agent may restart a pod autonomously (L4) while needing approval to fail over a database (L2).

L0 ObserveAgent watches and records what it would have done. Shadow mode only.
L1 RecommendDiagnosis and plan presented to a human who executes manually.
L2 ApproveAgent executes after a named human approves in Chat or ITSM.
L3 NotifyAgent executes, then notifies; human can roll back within a window.
L4 AutonomousAgent executes and closes. Reviewed by sampling and evals only.

Promotion rule. An action type moves up one level only after at least 200 executions (or 30 days) at the current level with ≥ 98% plan precision, zero severity-1 side effects, a tested rollback, and sign-off from the service owner. Any severity-1 caused by an agent demotes that action type two levels automatically.

Gateway responsibilities

  • Unified OpenAI-compatible and Vertex-native API for all agents
  • Per-agent token budgets and rate limits (Apigee), hard stops on runaway loops
  • Semantic cache in Memorystore keyed by embedding plus policy context
  • Prompt and response logging with DLP redaction before storage
  • Circuit breakers, retries with jitter, regional failover
  • Cost attribution labels: agent, use case, business unit

Model supply chain

  • All self-hosted weights scanned, signed and stored in Artifact Registry / Model Registry
  • Fine-tuning via Vertex AI tuning (Gemini) and Vertex AI Pipelines (open models, LoRA / QLoRA)
  • Every model version carries an evaluation card before it can be routed to
  • Shadow traffic: new versions receive mirrored requests and are scored offline before canary

8.3 Golden signals for agents

Operational

  • Episode success rate and latency (p50, p95)
  • Time to first token, tokens per second per model
  • Tool error rate and retry rate
  • Queue depth and age in Pub/Sub and Cloud Tasks
  • GPU / TPU utilisation, KV-cache utilisation

Quality

  • Plan precision (actions later judged correct)
  • Groundedness and faithfulness scores
  • Hallucinated tool or parameter rate
  • Human override and rollback rate
  • User feedback score from Chat and ITSM

Business

  • MTTD and MTTR by severity
  • Autonomous resolution rate
  • Toil hours removed per week
  • Change failure rate
  • Tickets deflected

Cost and safety

  • Cost per episode and per resolved incident
  • Cache hit rate and tier mix
  • Model Armor blocks, DLP findings
  • Policy denials and denied-then-retried attempts
  • Loop detection triggers and budget stops

8.4 Evaluation

Evaluation runs continuously, not just before release. Offline, every agent version runs against a golden set of replayed incidents in Vertex AI Pipelines and is scored by the Gen AI Evaluation Service (trajectory match, tool-use correctness, groundedness, safety) plus LLM-as-judge rubrics calibrated against human labels. Online, a sampled 5–10% of production episodes are scored asynchronously and every human override is turned into a new labelled test case. Quality metrics are exported to Cloud Monitoring so that a regression pages the owning team exactly like a latency regression.

9Scalability and resilience

Inference scaling

  • GKE with GPU and TPU node pools; Horizontal Pod Autoscaler on queue depth and KV-cache utilisation, not CPU
  • GKE Inference Gateway for model-aware load balancing and LoRA adapter routing on shared base models
  • Custom compute classes with fallback between accelerator types; DWS flex-start for batch fine-tuning
  • SLMs on Cloud Run GPU scale to zero outside business hours
  • Gemini Provisioned Throughput sized to p70 load; pay-as-you-go absorbs burst

Orchestration scaling

  • Agent Engine scales agent runtimes horizontally; agents are stateless between steps with state in Sessions
  • Pub/Sub decouples ingestion from reasoning; ordering keys per incident preserve sequence
  • Cloud Tasks for rate-limited tool calls to fragile downstream systems
  • Workflows for long-running, durable plans that survive restarts
  • Priority lanes: P1 events bypass batch queues and reserve capacity

Failure handling

  • Idempotency keys on every mutating tool call; exactly-once side-effect ledger in Spanner
  • Circuit breakers per model and per tool; graceful degradation to L1 recommend-only mode
  • Loop guards: maximum steps, tokens and wall-clock per episode
  • Global kill switch per agent and per action type, propagated in < 10 s
  • Dead-letter topics with automated replay after fixes

Multi-region and DR

  • Active-active in two regions for gateway, orchestration and tools behind global load balancing
  • Spanner multi-region for side-effect ledger and graph; BigQuery multi-region for the lake
  • Vertex AI endpoints in both regions; in-house LLM warm standby
  • RPO ≈ 0 for approvals and actions, RTO < 15 min for the platform
  • If the agent platform is down, operations fall back to existing human runbooks: agents are never a single point of failure

12Network and connectivity

12.1 Hybrid connectivity: Interconnect primary, HA VPN backup

On-premises and other clouds connect through a hub-and-spoke design anchored on Network Connectivity Center. Dedicated Interconnect in the 99.99% topology (four circuits across two metros and two regions) carries production traffic with MACsec encryption at layer 2. HA VPN tunnels over the internet provide an encrypted backup path with lower BGP preference, and serve smaller sites and partners that cannot justify an Interconnect. Cross-Cloud Interconnect links to AWS and Azure where agents need to act on workloads there.

12.3 Private access to Google and platform services

  • Google APIs. A PSC endpoint for the vpc-sc API bundle, with private Cloud DNS zones mapping *.googleapis.com to it. Vertex AI, BigQuery, Storage and all other API calls stay on Google's network and are forced through VPC-SC checks.
  • On-prem to Google APIs. On-prem DNS forwards googleapis.com to Cloud DNS inbound forwarders; Cloud Routers advertise the PSC endpoint range over Interconnect, so on-prem collectors can write telemetry without internet paths.
  • Apigee X. Northbound through the global ALB; southbound to agents through PSC, with no VPC peering between Apigee's tenant network and ours.
  • MCP tool reach. Tools that must act inside a business unit's VPC are published as PSC service attachments from that VPC, so the platform gets one IP per tool with no broad network routes to workload subnets.
  • DNS security. Private zones per environment, DNSSEC on public zones, and DNS response policies that block resolution of unapproved external domains from the platform core.

12.5 Egress control

Egress is denied by default at the hierarchical firewall policy. Model-serving nodes and the restricted enclave have no egress at all. Agents and MCP tools that must call SaaS go through Secure Web Proxy with an FQDN allow-list per tool service account (for example only the ServiceNow instance for the ITSM executor), TLS inspection where policy allows, and Cloud NAT with static IPs that SaaS vendors can allow-list. Model weights and container images are never pulled at runtime; they enter only through the build project, are scanned and signed, and are served from Artifact Registry.

12.6 East-west and microsegmentation

Inside the perimeter, Cloud Service Mesh enforces mTLS with workload identities for every hop, and authorization policies state which agent may call which tool service (for example the incident agent may call the Kubernetes executor but not the IAM executor). Cloud NGFW network firewall policies use IAM-governed secure tags rather than IP ranges, so a compromised workload cannot relabel itself into a broader rule.

12.7 Administrative access

There are no bastion hosts with public IPs and no standing admin roles. Engineers reach the console and APIs through Chrome Enterprise Premium with context-aware access, reach VMs and nodes through IAP TCP forwarding, and gain elevated roles only through Privileged Access Manager with a justification, an approver and an expiry. Two break-glass accounts protected by hardware security keys exist per perimeter; any use pages the security on-call and opens a SecOps case automatically.

13.5 Detection and response for the agent platform

  • Network telemetry. VPC Flow Logs on all subnets, Cloud NGFW IPS threat logs, Packet Mirroring into Cloud IDS for the restricted enclave, Interconnect and VPN tunnel metrics in Cloud Monitoring.
  • Posture. Security Command Center Enterprise with AI protection for model, agent and dataset inventory, misconfiguration findings, and toxic-combination analysis.
  • Agent-specific detections in Google SecOps. An agent calling a tool it has never used, a spike in policy denials, privileged actions outside change windows, token spend far above baseline, repeated Model Armor findings from one data source, or an executor credential used from an unexpected network.
  • Automated containment. SOAR playbooks can flip an agent's kill switch, disable its service account, revoke PAM grants, isolate a workload with a deny tag, or pin the router to recommend-only mode, all in under a minute.
  • Evidence. Audit and agent-lake logs are written to locked log buckets with retention policies, giving tamper-evident records for investigations and regulators.

16FinOps for intelligence

  • Attribute everything. Labels on every model call (agent, use case, cost centre) flow into BigQuery billing export joined with the agent lake, giving cost per resolved incident and per business outcome.
  • Push work down the tiers. Target 70%+ of tokens on SLMs and cache; review the tier mix monthly and distil frequent Gemini tasks into SLMs.
  • Buy baseline, rent burst. Provisioned Throughput and committed-use discounts for GPUs/TPUs cover steady load; spot and DWS flex-start for training and batch evaluation.
  • Budgets as guardrails. Per-agent daily token budgets enforced at the gateway, with Cloud Billing budgets and Pub/Sub alerts on anomalies.
  • Context discipline. Context caching for large stable prompts, retrieval over stuffing, and summarised memory rather than raw history.
