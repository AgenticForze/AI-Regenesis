Agentic Operations Platform on AWS

The AWS edition of our enterprise Agentic Ops reference architecture: governed AI agents running IT, cloud and business operations on Amazon Bedrock and Bedrock AgentCore, with in-house LLMs and SLMs on EKS for workloads that must stay inside our boundary, and the full AWS network, security and observability estate around them.

Owner Office of the CTO, Enterprise Architecture Status Target-state blueprint v1.0 Companion Google Cloud edition

1Intent and principles

Agentic Ops replaces ticket-driven, human-routed operations with a mesh of specialised agents that observe signals, reason over enterprise context, plan, act through governed tools, and learn from outcomes. The principles are cloud-neutral and identical to the Google Cloud edition; only the services change.

Agents are workloads

Every agent has an IAM identity, a versioned spec, an SLO, a budget, an owner and a kill switch, and runs in AgentCore Runtime like any production service.

Right model for the job

SLMs on Inferentia for volume, in-house LLMs on EKS for restricted data, Bedrock models (Amazon Nova, Anthropic Claude and others) for deep reasoning. One gateway decides.

Autonomy is earned

Each action type starts in shadow mode and graduates through autonomy levels based on measured precision, blast radius and reversibility.

Everything is a trace

AgentCore Observability and ADOT emit OpenTelemetry spans for every step, joined by one trace ID from alarm to outcome in X-Ray and CloudWatch.

Policy outside the prompt

AgentCore Policy (Cedar) intercepts every tool call, and SCPs and IAM boundaries cap what any agent role can ever do, regardless of what the model says.

Open protocols

MCP through AgentCore Gateway, A2A between agents, OpenTelemetry, OCI images and Terraform or CDK keep every seam portable.

3End-to-end flow

A CloudWatch alarm, ticket, chat message or EventBridge event enters through the edge, passes Bedrock Guardrails, is triaged by an SLM and handed to the supervisor on AgentCore Runtime. The supervisor delegates over A2A, domain agents ground themselves in Knowledge Bases, Neptune topology and AgentCore Memory, and every proposed action is checked by AgentCore Policy before an MCP tool behind AgentCore Gateway touches production.

Figure 1. Signal-to-outcome flow on AWS. Dotted lines are asynchronous telemetry and learning paths.

Autonomy levels

L0 ObserveShadow mode; AgentCore Policy in log-only mode.
L1 RecommendPlan presented; a human executes.
L2 ApproveExecutes after a named approver responds to a Step Functions task token.
L3 NotifyExecutes, then notifies, with a rollback window.
L4 AutonomousExecutes and closes; reviewed by sampling and evaluations.

Promotion rule. One level up after 200 executions or 30 days at ≥ 98% plan precision, zero severity-1 side effects, a tested rollback and service-owner sign-off. Any agent-caused severity-1 demotes that action type two levels automatically.

9Scalability and resilience

Inference scaling

  • EKS with Karpenter node pools across Inferentia, Trainium and GPU instance families
  • KEDA scaling on queue depth and KV-cache utilisation
  • Bedrock cross-Region inference profiles absorb burst
  • Provisioned Throughput sized to steady baseline
  • Capacity Blocks or Savings Plans for reserved accelerators

Orchestration scaling

  • AgentCore Runtime isolates each session in its own microVM and scales automatically
  • EventBridge and SQS decouple ingest from reasoning; FIFO groups per incident
  • Step Functions for long-running durable plans
  • Priority queues reserve capacity for P1

Failure handling

  • Idempotency keys and a DynamoDB side-effect ledger
  • Circuit breakers per model and tool; degrade to recommend-only
  • Step, token and time caps per episode
  • Kill switch via AppConfig feature flags, < 10 s propagation
  • DLQs with replay

Multi-Region and DR

  • Active-active in two Regions behind Route 53 health-checked routing
  • DynamoDB global tables for ledger and approvals
  • Aurora Global Database and Neptune replicas
  • RPO ≈ 0 for actions, RTO < 15 min
  • Human runbooks remain the fallback

12Network and connectivity

12.1 Direct Connect primary, Site-to-Site VPN backup

Data centres connect through Dedicated Direct Connect in the maximum-resiliency model: four connections across two Direct Connect locations per Region pair, with MACsec on 10 and 100 Gbps ports. Transit virtual interfaces land on a Direct Connect gateway associated with Transit Gateways in each Region. Accelerated Site-to-Site VPN attachments on the Transit Gateways carry the same prefixes with a longer AS path, so they only take traffic when Direct Connect fails; they also serve branches and partners. Cloud WAN can replace per-Region Transit Gateways for global segmentation as the estate grows.

Figure 10. Hybrid transit on AWS. VPN paths are dashed amber; the enclave is reachable only through PrivateLink.

12.3 Private access, egress and east-west

  • AWS services. Interface endpoints for Bedrock runtime, AgentCore, STS, KMS, Secrets Manager, CloudWatch, SSM and others, plus gateway endpoints for S3 and DynamoDB, all with endpoint policies restricted to our organisation.
  • DNS. Route 53 Resolver inbound and outbound endpoints for hybrid resolution, private hosted zones shared through RAM, and Route 53 Resolver DNS Firewall blocking unapproved domains.
  • Egress. Denied by default. SaaS calls from executors leave through the egress VPC, where Network Firewall stateful rules allow only listed SNI domains per source CIDR, and NAT gateways present fixed IPs that SaaS vendors can allow-list. Model and enclave subnets have no egress path.
  • East-west. VPC Lattice service networks with IAM auth policies define which agent may call which tool; security groups reference each other rather than CIDRs.
  • Admin access. No bastions: Systems Manager Session Manager for instances and nodes, Verified Access for internal web tools, temporary elevated access through an approval workflow on IAM Identity Center permission sets, and break-glass IAM users with hardware MFA monitored by GuardDuty and EventBridge.

13.5 Detection and response

  • Signals. VPC Flow Logs, Network Firewall alerts, Route 53 Resolver query logs, CloudTrail data events, GuardDuty (including EKS runtime and Lambda protection), Inspector and Macie findings, all normalised to OCSF in Security Lake.
  • Agent-specific detections. New tool usage by an agent, spikes in Cedar denials or Guardrails interventions, privileged API calls outside change windows, token spend far above baseline, or an executor role used from an unexpected VPC endpoint.
  • Automated containment. EventBridge rules trigger Step Functions or SOAR playbooks that flip the AppConfig kill switch, attach a deny-all session policy, revoke Identity Center sessions, or isolate a workload's security group.

16FinOps for intelligence

  • Attribute everything. Cost-allocation tags and Bedrock application inference profiles per agent and use case, joined with the agent lake in Athena for cost per resolved incident.
  • Push work down the tiers. Target 70%+ of tokens on SLMs and cache; use Bedrock Model Distillation to move frequent frontier tasks into smaller models.
  • Buy baseline, rent burst. Provisioned Throughput and Savings Plans for steady load; Spot and Capacity Blocks for training and batch evaluation; Bedrock batch inference at lower cost for offline scoring.
  • Budgets as guardrails. AWS Budgets actions and Cost Anomaly Detection alerts, plus hard per-agent token caps at the gateway.
  • Context discipline. Prompt caching, retrieval over stuffing, summarised memory.
